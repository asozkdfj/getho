# v0.2.0 모델 성능·평가 방법·개선 방향 분석

검토일: 2026-10-16 (한국 시간). 개발 기준 커밋: `d8a72cae2cdfcb1db655dbf25213d9d89aed097d` (`claude/epl-edge-lab-mvp-xtnbpy`).

## 판단

**v0.2.0은 기본 비율보다 유용한 확률을 내는 통계 기준 모델입니다. 다만 시장 대비 우위, 현재 운영 픽 적중률, 선발 명단 추가의 안정적 개선까지 입증된 단계는 아닙니다.** 현 시점에는 LLM을 확률 생성기로 교체하기보다 평가 조건을 운영과 맞추고, 리그별 오차 원인을 나눠 검증하는 작업이 우선입니다.

이 문서는 저장된 평가 JSON과 소스를 분석한 결과입니다. 전체 모델 재학습·전체 백테스트 재실행·운영 DB 조회는 하지 않았습니다. Docker를 사용하지 않았습니다. 요약 수치를 재계산하고 원본 픽 함수로 선정 시각 차이를 보여주는 합성 반례를 실행했습니다. 모델 파라미터와 서비스 동작은 변경하지 않았습니다.

## 1. 실제 운영 모델

[model.py](../../ml/edge_ml/model.py)에 `MODEL_VERSION = "0.2.0"`이 선언되어 있습니다. LLM이 아니라 다음 구조입니다.

1. 과거 득실점으로 팀별 공격·수비 강도와 리그 홈/원정 득점률을 추정합니다.
2. 같은 경기 이력으로 Elo를 계산합니다.
3. Poisson의 득점 우위와 Elo의 전력 차이를 기대 득점 단계에서 결합합니다. Poisson 가중치 0.6, Elo 환산 계수 280입니다.
4. 득점 분포를 홈승/무/원정승 확률로 변환합니다.
5. 운영 보정은 identity이며, 승격·미관측 팀에는 하위권 강도 prior를 사용합니다.

시간 가중치 0.005/일의 반감기는 약 139일입니다. 리그마다 같은 파라미터를 사용해 별도 학습하며, 컵 대회는 예측하지 않습니다. 현재 명단·부상 정보는 화면에만 표시되고 운영 확률에는 쓰이지 않습니다.

## 2. 성능 수치와 올바른 해석

출처는 [기존 전체 평가 JSON](../../ml/reports/backtest-openfootball.json)입니다. 생성 시각은 2026-10-16 07:40 KST이고, EPL 시험 구간은 2023-08-11~2026-05-24 UTC, 1,140경기입니다. 이것은 과거 시험 구간 성적이며 2026-27 실시간 성적이 아닙니다.

| --- | --- | --- | --- | --- |
| 기본 비율 | 1.0737 | 0.6499 | 43.16% | 0.0142 |
| Elo만 | 0.9865 | 0.5879 | 52.11% | 0.0235 |

- 기본 비율 대비 log loss 상대 감소는 **8.43%**, 적중률 차이는 **+9.04%p**입니다. 모델이 결과를 구별하는 신호는 있습니다. 단순 균등 33.3%보다 이 기본 비율 기준선과 비교하는 편이 적절합니다.
- 기본 비율과 운영 모델의 paired log loss 차이(base−production)는 **+0.09048, 95% CI [+0.07129, +0.10948]**입니다. 저장된 경기 단위 bootstrap 가정하에서 개선 근거가 있습니다.
- Poisson만 쓴 모델 대비 개선은 **0.00021**이고 CI는 **[−0.00244, +0.00284]**로 0을 포함합니다. 현재 복합 모델의 추가 이득은 뚜렷하지 않습니다. 이것이 바로 Poisson으로 교체해야 한다는 뜻도 아닙니다.

### 리그별 차이가 있음

10개 리그의 시험 표본은 합계 **9,912경기**입니다. 저장된 리그별 적중률을 경기 수로 가중한 값은 **50.87%**이며, 하루 한 픽 성적과는 다른 지표입니다.

- Championship: 운영 1.0521, Elo만 1.0484 → 운영 모델이 약 0.0037 나쁩니다.
- Ligue 1: 운영 1.0065, Elo만 0.9999 → 운영 모델이 약 0.0065 나쁩니다.
- 다른 리그에서는 평균적으로 운영 모델이 Elo만보다 낮은 log loss를 보이지만, 리그별 Elo 대비 paired CI는 저장된 요약에 없어 유의성을 판단할 수 없습니다.

따라서 ‘10개 리그 검증됨’은 **기본 비율보다 좋다는 현재 기준을 통과했다**는 뜻이며 시장보다 좋거나 모든 단순 모델보다 좋다는 뜻은 아닙니다. 리그별로 유리한 모델을 이번 시험 성적만 보고 바로 선택하면 같은 시험 집합에 맞추는 문제가 생깁니다. 이후 구간에서 검증해야 합니다.

## 3. 평가 신뢰성을 먼저 보강할 부분

### A. 오늘의 픽 백테스트와 실제 선정 시각이 다름 — 최우선

[backtest_daily_picks](../../ml/edge_ml/picks.py)는 KST 날짜로 묶은 **하루 전체 경기**에서 가장 큰 확률을 선택합니다. 선정 시각과 데이터 수집 상태를 인자로 받지 않습니다.

반면 [운영 publish_daily_pick](../../apps/api/edge_api/services/picks.py)은 실제 선정 시점에 [quality.assess](../../apps/api/edge_api/services/quality.py)를 거쳐 `kickoff_at > now`, 최신 배당, 최근 수집 성공, 현재 모델, 팀 이력 등의 조건을 통과한 후보만 선택합니다. 기본 선정 시각은 09:00 KST입니다.

합성 반례: 같은 날 02:00 경기 확률 90%, 20:00 경기 확률 60%이면 현재 백테스트는 02:00 경기를 고릅니다. 09:00에 동작하는 실제 서비스는 이미 시작한 02:00 경기를 제외합니다. [감사 스크립트](../../scripts/qa/audit_model_v020.py)로 원본 함수를 실행해 확인했습니다. 이 예시는 조건 차이를 입증하는 용도이며 성능 추정이 아닙니다.

**저장된 75.27% = 414/550픽, Wilson CI 71.50~78.69%는 현재 백테스트 규칙의 결과입니다. 현재 운영 방식의 검증된 적중률로 직접 인용하면 안 됩니다.** 유럽 경기의 KST 새벽 시간대를 생각하면 무시하기 어려운 차이입니다. 수정 후 수치가 얼마나 달라지는지, 높아질지 낮아질지는 실제 재평가 전에는 알 수 없습니다.

필요한 수정/재평가:

- 날짜별 decision_at을 만들고 그때 아직 시작하지 않은 경기만 후보에 포함.
- 예측·배당·경기 결과가 해당 시점에 실제로 알려졌는지 확인.
- 당시 품질 게이트를 재현할 수 없으면, 전체 후보 기준 이상적 백테스트와 운영 재현 백테스트를 나눠 명시.
- 서비스가 늦게 켜져 09:00보다 늦게 선정되는 경우도 별도 기록.
- 픽을 09:00~다음 날 09:00 구간으로 바꾸고 싶다면 기존 자정 기준 규칙과 별개의 정책으로 정의·평가.

### B. 테스트를 선택에도 쓰는 구조

[backtest_cli.py](../../workers/ingestion/edge_ingestion/backtest_cli.py)는 시험 결과로 리그 verified를 정하고, 그 리그의 **같은 시험 예측**을 모아 픽 성적을 계산합니다. 이번에는 10개 모두 통과해 실제 선택 편향 크기는 추정할 수 없지만, 리그를 더 늘리면 통과한 집합만 보고하는 선택 문제가 커질 수 있습니다.

또한 기존 ADR-012는 시험 구간의 적중률 하한으로 0.55 기준을 정했다고 기록합니다. 따라서 픽 규칙 전체가 완전히 독립적인 시험 집합에서 한 번만 평가됐다고 보기는 어렵습니다. 이는 경기 예측 모델의 walk-forward 학습 자체에 미래 결과가 들어갔다고 단정하는 것과는 다른 문제입니다.

권장: 내부 과거 구간에서 파라미터·리그 범위·픽 임계값을 선택하고 다음 외부 시간 구간에서 전체 파이프라인을 평가합니다. 이미 확인한 2023-26 시험 구간은 후속 개발의 검증 구간으로 취급하고, 이후 미사용 구간/향후 기록을 최종 확인에 남깁니다. [테스트 데이터로 모델 선택을 하지 않아야 하는 이유](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)

### C. 신뢰구간과 교체 기준의 의미

[promotion.py](../../ml/edge_ml/promotion.py)는 log loss CI 상한이 0 미만이거나, 평균 개선이 0.002 이상이면 통과할 수 있습니다. 별도로 CI 상한 0.005 이하, Brier 비악화, ECE 증가 0.01 이하를 확인합니다.

이 규칙은 **통계적 유의성만을 요구하는 규칙이 아닙니다.** 평균 개선이 작지만 기준을 넘으면 CI가 0을 포함해도 승격이 가능합니다. `promote=true`를 ‘개선 확정’으로 읽지 않아야 합니다. 연구 후보/그림자 운영 후보/정식 교체를 나누고, 정식 교체에는 효과 크기와 독립 시험 구간의 불확실성을 함께 판단하는 편이 좋습니다.

[metrics.py](../../ml/edge_ml/metrics.py)는 경기 단위 iid bootstrap을 사용합니다. 같은 팀의 반복 경기와 같은 주의 공통 조건이 있으므로 주·라운드 단위 paired block bootstrap을 함께 계산해 CI가 얼마나 달라지는지 확인할 것을 권합니다. 현재 CI가 반드시 과소평가됐다는 결론은 아닙니다.

### D. 데이터와 운영 조건 차이

- 과거 데이터에는 배당이 0건입니다. **시장 확률 대비 우위는 측정되지 않았습니다.** 같은 의사결정 시각의 시장 확률을 기준선으로 추가해야 합니다. 09:00 예측과 킥오프 직전 종가 배당은 정보량이 다르므로 분리 비교합니다.
- 결과 이력으로 재구성한 walk-forward와 운영 수집 시각은 다릅니다. `kickoff < as_of`는 결과가 수집된 시각까지 보장하지 않습니다. 결과 가용 시각/최소 종료 지연을 기록하거나 보수적으로 제한합니다.
- 백테스트는 긴 누적 이력으로 주마다 재학습합니다. 운영은 DB에 수집된 이력으로 매 작업 때 학습하므로 이력 길이와 refit 빈도를 맞춘 실험이 필요합니다.
- Championship의 557경기/반복 대진은 플레이오프 가능성이 있습니다. 단순 중복 오류로 삭제하지 말고 단계·중립 구장·규정상 연장 포함 여부를 확인해야 합니다. 2. Bundesliga 2025-26은 99경기만 있어 시즌 누락과 표본 대표성을 확인해야 합니다.
- 지금의 결과 JSON에는 최종 요약이 있지만, 모든 경기의 예측 벡터·학습 기준 시각·선정 제외 사유는 담겨 있지 않습니다. 다음 실행부터 per-match 산출물과 원본 데이터 커밋/파일 해시를 저장해야 임의 하위집단과 paired CI를 다시 계산할 수 있습니다.

## 4. 기존 실험에서 배울 점

### 파라미터 탐색과 확률 보정

현재 좌표 탐색에서는 채택 기준을 넘는 변경이 없었습니다. 다만 ‘현재 모델이 거의 최적’이라는 기존 문구는 **탐색한 범위와 순차 탐색 절차 안에서**라는 조건이 필요합니다. 상호작용·다른 구조·새 정보까지 최적이라는 뜻은 아닙니다.

Temperature T=0.9467은 EPL 시험 log loss를 0.000246 낮췄고 paired CI는 [−0.001599, +0.001153]입니다. 통계적으로 확정되지 않았고 2025-26 시즌에서는 오히려 악화됐습니다. 전역 temperature를 지금 적용할 근거는 약합니다. Isotonic도 자동 개선 수단이 아니며 표본이 적으면 과적합될 수 있습니다. [보정 방법과 데이터 조건](https://scikit-learn.org/stable/modules/calibration.html)

승격팀 prior를 끄면 log loss가 0.002994 나빠지는 쪽이지만 CI [−0.000758, +0.006652]는 0을 포함합니다. 설명 가능한 현행 prior를 유지하며 승격팀/시즌 초반 하위집단에서 다시 보는 방향이 적절합니다.

### 선발 명단 실험

[명단 평가 JSON](../../ml/reports/backtest-lineups-statsbomb.json)은 StatsBomb open data 2015-16 4개 리그를 사용합니다. β=0.2123, γ=0.1761, 검증 488경기이며 주전 강도를 최근 출전 시간 비중으로 요약합니다.

| 합산 시험 613경기 | 운영 | 운영 + 명단 |
| --- | --- | --- |
| Log loss ↓ | 0.9918 | 0.9894 |
| Brier ↓ | 0.5902 | 0.5885 |
| 적중률 | 약 52.0% | 약 51.9% |
| ECE ↓ | 0.0336 | 0.0355 |

평균 log loss 차이는 **−0.002429, 95% CI [−0.005349, +0.000574]**로 개선 가능성은 있지만 확정되지 않았습니다. EPL은 1.0052→1.0076으로 악화됐고 다른 3개 리그는 개선됐습니다. 55/60/65% 분할 모두 정책을 통과하더라도, 시험 표본이 겹쳐 독립 검증 3회와 같지 않습니다.

명단 계수를 여러 리그의 각기 다른 날짜 구간에서 함께 학습하므로, 가장 이른 시험 예측보다 늦게 끝나는 다른 리그의 검증 데이터가 포함되는지도 타임스탬프로 확인할 필요가 있습니다. 현재 요약만으로 실제 교차 여부는 확정하지 않았습니다.

추천은 **즉시 전체 적용보다 그림자 평가**입니다. 최신 복수 시즌·운영 provider 자료에서 확인하고, 명단 발표 전 모델과 발표 후 모델을 별도 평가합니다. 09:00에 고정되는 픽에 나중에 발표되는 명단을 넣으면 미래 정보 사용이 됩니다.

## 5. 개선 우선순위와 실험 설계

| 순서 | 작업 | 기대 효과의 종류 | 확인 기준 |
| --- | --- | --- | --- |
| 1 | 운영 시각/가용 데이터/품질 게이트를 재현하는 평가 | 성과 수치의 신뢰성 확보 | 원본 후보·제외 사유·선정 시각이 저장되고 운영과 동일한 후보를 선택 |
| 2 | 리그·시즌·승격팀·홈무원정·확률 구간별 오차 분석 | 개선할 문제의 위치 확인 | 경기별 예측과 손실을 남겨 2025-26 악화 요인을 분해 |
| 3 | 리그별 단순 기준선/제한된 가중치 탐색 | 불필요한 복잡도 제거 또는 지역화 | Elo·Poisson·운영을 동일 표본에서 비교, 외부 시간 구간 log loss/Brier 확인 |
| 4 | 시점이 일치하는 배당·xG·휴식/일정·선수 자료 추가 | 기존 결과 이력에 없는 정보 추가 | 한 번에 한 특성군의 ablation, 수집 가능 시각과 결측 처리 고정 |
| 5 | 선발 발표 후 보정 모델 그림자 운영 | 명단 정보의 순수 추가 가치 측정 | 현행 모델과 같은 경기/같은 시각에서 paired 비교, 리그별 비악화 확인 |
| 6 | 구간별 보정 및 소규모 앙상블 | 확률의 신뢰도 개선 | 학습에 쓰지 않은 시간 구간에서 log loss/Brier와 보정표 함께 개선 |

이 순서는 성공을 보장하는 예측이 아니라 현재 증거에 따른 연구 우선순위입니다. 리그별로 파라미터를 자유롭게 늘리기보다 공통값으로 수축시키는 제한된 탐색부터 시작하는 편이 과적합을 통제하기 쉽습니다. 이미 효과가 작았던 전역 temperature·Dixon–Coles 등을 근거 없이 재채택하지 않습니다.

외부 시간 구간 평가 전에 실험 수와 주 지표를 고정하고, 모든 후보 결과를 기록합니다. 1차 기준은 log loss, 보조 기준은 Brier·구간별 calibration·coverage입니다. 예측을 덜 내서 적중률만 높이는 방식은 모델 자체의 개선과 구분합니다.

## 6. LLM을 쓴다면 맡길 역할

현재처럼 구조화된 득실점·명단 API가 있다면 먼저 그 데이터를 직접 쓰는 것이 자연스럽습니다. LLM 도입은 비정형 뉴스에서 추가 정보를 안정적으로 뽑을 수 있을 때 검토합니다.

- 입력: 실제 예측 시점 이전에 공개된 기사·공식 발표.
- 추출: 팀/선수 ID, 부상·징계·출전 불투명 여부, 예상 기간, 기사 발행 시각, 원문 근거.
- 검증: 모르는 내용은 미확인 처리, 출처 없는 추정은 제외, 상충 보도는 보존. 결과 공개 후 기사를 과거 입력으로 섞지 않기.
- 평가: 선수 식별/상태 분류 정확도·precision/recall, 시간 정보 오류, 근거 없는 주장 비율, 미확인 처리율을 먼저 측정.
- 모델 결합: 검증된 추출 결과를 특성으로 넣고 기존 모델 대비 추가 가치만 따로 검증.
- 사용자 설명: 확률과 근거는 저장된 수치/출처에 연결하고 LLM이 임의로 확률을 수정하지 않도록 구성.

스포츠 요약 연구도 입력 구조에 따른 사실 오류를 별도로 평가합니다. 따라서 자연스러운 문장 생성 능력과 예측 성능은 분리해 검증해야 합니다. 위 LLM 설계는 현재 코드에 대한 제안이며 성능 향상이 측정된 결과는 아닙니다. [관련 원문 연구](https://aclanthology.org/2025.inlg-main.46/)
