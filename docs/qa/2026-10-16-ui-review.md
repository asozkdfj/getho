## 발견 항목

### QA-01 — 선택을 바꿔도 이전 조합의 응답이 표시됨

**근거:** [CombinationBuilder.tsx](../../apps/web/components/CombinationBuilder.tsx)의 `pick`, `analyze`, 선택·초기화 버튼.

- 조건: A 조합으로 분석 요청 → 응답 전에 B 조합으로 선택 변경 또는 초기화 → A 응답 도착.
- 원인: `pick`/초기화는 현재 결과만 지우고, 진행 중인 요청을 취소하거나 선택 버전을 무효화하지 않습니다. 이전 응답은 그대로 `setResult`를 호출합니다. 로딩 중에도 선택과 초기화는 가능합니다.
- 영향: 현재 선택과 다른 조합의 확률·배당·기대값이 나옵니다. 최신 코드에서는 결과가 도착하면 자동 스크롤과 포커스까지 이동하므로 이전 응답에도 화면이 이동합니다.
- 권장: 요청 ID/선택 버전을 비교해 유효한 응답만 반영하고 취소를 함께 처리합니다. 단순한 대안은 계산 중 선택·초기화를 잠그는 것입니다.
- 완료 기준: 지연 응답 도중 선택 변경 또는 초기화 후 이전 결과·오류·자동 이동이 발생하지 않아야 합니다.

### QA-02 — 선택 화면과 실제 계산의 배당 기준이 다름

**근거:** [CombinationBuilder.tsx](../../apps/web/components/CombinationBuilder.tsx)의 `f.latest_odds`, [fixtures.py](../../apps/api/edge_api/api/routes/fixtures.py)의 최신 배당 조회, [combinations.py](../../apps/api/edge_api/services/combinations.py)의 `snapshot = prediction.odds_snapshot`.

- 조건: 예측이 저장된 후 새로운 배당 스냅샷이 수집되고 아직 예측은 갱신되지 않은 시점.
- 현상: 선택 버튼에는 최신 배당이 표시되지만 계산은 저장된 예측에 연결된 배당으로 수행됩니다. 예: 선택 시 홈승 2.10, 예측 연결 배당 1.90이면 결과 leg는 1.90입니다.
- 영향: 사용자가 보고 선택한 가격과 조합 배당·기대값이 달라집니다. 결과의 배당 기준 시각 표시는 사전 불일치를 해결하지 않습니다.
- 권장: 선택 API에 실제 계산에 쓰는 배당과 기준 시각을 함께 제공하거나, 계산 정책 자체를 바꾸되 선택 화면과 일치시킵니다.
- 완료 기준: 서로 다른 두 배당 스냅샷이 있을 때 선택에 표시한 값과 결과의 계산 기준이 일치하거나, 갱신 필요를 명확히 알리고 재확인해야 합니다.

### QA-03 — 부가 패널의 실패가 핵심 경기 목록을 가림

**근거:** [홈 page.tsx](../../apps/web/app/page.tsx)의 `Promise.all`, [리그 상세 page.tsx](../../apps/web/app/leagues/[id]/page.tsx)의 `Promise.all`.

- 조건: 경기 조회 정상, 하이라이트 조회 실패 또는 타임아웃.
- 원인: `fetchHighlights`가 격리되지 않아 Promise 전체가 거부되고 페이지 오류 화면으로 이동합니다. 홈의 픽/상태/리그 정보는 이미 `orNull`로 격리되어 있습니다.
- 권장: 하이라이트를 개별 오류 상태로 표시하고 경기 목록을 유지합니다. 실패와 정상 빈 결과를 구분합니다.
- 완료 기준: 하이라이트만 실패해도 홈·리그 상세의 경기 목록이 보여야 합니다.

### QA-04 — 날짜 그룹은 서버 시간대, 시각은 브라우저 시간대

**근거:** [leagues.ts](../../apps/web/lib/leagues.ts)의 `groupByDayAndLeague`, [LocalTime.tsx](../../apps/web/components/LocalTime.tsx)의 `browserTz`, [FixtureCard.tsx](../../apps/web/components/FixtureCard.tsx)의 `format="time"`.

- 조건: 브라우저 시간대가 `DEFAULT_TZ`와 다른 사용자가 자정 부근 경기를 조회.
- 현상: 예를 들어 한국 시간 10월 17일 00:30 경기는 서울 기준 17일에 묶이지만, 런던 브라우저에서는 전날 시각으로 바뀝니다. 카드는 날짜 없이 시각만 표시하며 홈 설명은 여전히 서버 시간대를 안내합니다.
- 권장: 조회 날짜·그룹·표시 시각을 같은 시간대로 통일합니다. 사용자 시간대를 지원하려면 조회 기간도 함께 맞춥니다.
- 완료 기준: 서울/런던 환경에서 날짜 경계 경기를 비교했을 때 날짜 제목과 시각의 기준이 일치해야 합니다.

### QA-05 — 상세 화면이 데이터 품질 검사 결과를 표시하지 않음

**근거:** [fixtures.py](../../apps/api/edge_api/api/routes/fixtures.py)의 `out.quality`, [경기 상세 page.tsx](../../apps/web/app/fixtures/[id]/page.tsx), [explain.ts](../../apps/web/lib/explain.ts).

- 조건: 오래된 배당·수집 지연 등 품질 검사 실패가 있지만 저장된 예측은 존재.
- 현상: API는 실패 사유를 반환하지만 상세 요약과 주의 문구에서는 사용하지 않습니다. 직접 링크로 접근하면 홈의 데이터 상태 안내도 거치지 않습니다. 새 시뮬레이션도 해당 상세 화면에서 제공됩니다.
- 권장: 상세 요약 위에 검사 결과와 기준 시각을 표시합니다. 종료 경기의 과거 분석과 예정 경기의 오래된 분석을 구분해 안내합니다.
- 완료 기준: quality 실패 응답에서 해당 실패 사유가 보이고, 정상 분석과 같은 상태로 오해하지 않아야 합니다.

### QA-06 — 하이라이트가 비면 ‘시장과 생각이 비슷하다’고 단정

**근거:** [Highlights.tsx](../../apps/web/components/Highlights.tsx)의 빈 배열 문구, [services/highlights.py](../../apps/api/edge_api/services/highlights.py)의 예측 유무·경기 상태·최소 차이 필터.

- 현상: 경기 없음, 예측 없음, 후보 제외, 차이 기준 미충족 모두 빈 배열이 될 수 있는데 ‘둘의 시각이 비슷하다는 뜻’이라고 단정합니다.
- 권장: 기본 문구를 ‘표시할 분석 결과가 없습니다’로 바꾸고 가능하면 API에 빈 결과 사유를 추가합니다.
- 완료 기준: 예측이 없는 경우 시장과 모델이 유사하다고 안내하지 않아야 합니다.

### QA-07 — 주전 판단 불가와 출전 불투명을 비주전으로 안내

**근거:** [teamNews.ts](../../apps/web/lib/teamNews.ts)의 `sideSummary`, [services/team_news.py](../../apps/api/edge_api/services/team_news.py)의 `known`, `regular_ids`, `out_ids`.

두 입력 경로에서 잘못된 안내를 확인했습니다.

1. 주전 판단 기록이 부족한 `regulars_known=false`이고 결장 목록이 있으면, 함수 끝에서 ‘평소 주전은 아님’으로 표시합니다. 서버는 이 경우 주전 집합을 비우므로 `regular=false`는 비주전으로 확인됐다는 뜻이 아닙니다.
2. `regulars_known=true`이고 알려진 주전이 `doubtful`이면, 서버의 `missing_regulars`는 확정 결장(`out`)만 포함하므로 빈 배열입니다. 이 경우에도 ‘평소 주전은 아님’으로 표시됩니다.

실제 원본 함수에 아래 입력을 넣어 Node.js 24.16.0에서 실행했습니다. 두 경우 모두 `결장·출전 불투명 1명 (평소 주전은 아님)`이 출력됐습니다. 앱/DB는 실행하지 않았습니다.

```js
const { sideSummary } = require('./apps/web/lib/teamNews.ts');
const base = {
  team_id: 1, team_name: 'Team', starters: [], missing_regulars: [],
  absences: [{ player_id: '1', name: 'Player', status: 'doubtful', regular: false }],
  regulars_known: false, recent_matches: 0,
};
console.log(sideSummary(base));
console.log(sideSummary({
  ...base, regulars_known: true, recent_matches: 10,
  absences: [{ ...base.absences[0], regular: true }],
}));
```

- 영향: 실제로는 판단할 수 없거나 주전 출전이 불투명한 상황을 비주전 결장으로 축소합니다.
- 권장: 기록 부족은 ‘주전 여부 판단 불가’, 주전 doubtful은 ‘주전 출전 불투명’으로 나누고 `absences[].regular` 및 `status`를 함께 사용합니다.
- 완료 기준: 위 두 입력에 비주전 확정 문구가 나오지 않고 각각의 상태를 정확히 표시해야 합니다. 기존 단위 테스트에는 이 두 경계 입력을 추가할 수 있습니다.

### QA-08 — 모바일 글자 크기가 기본값으로 덮임

**근거:** [globals.css](../../apps/web/app/globals.css)의 520px 미디어 쿼리와 그 뒤의 `.pick-prob-value`, `.pick-outcome` 선언.

- 현상: 모바일 미디어 쿼리에서 1.6rem/1.15rem을 선언하지만 뒤의 동일 선택자가 2rem/1.35rem으로 덮습니다. 미디어 쿼리 자체가 선택자 우선순위를 높이지 않습니다.
- 권장: 모바일 재정의를 기본 컴포넌트 선언 뒤로 옮깁니다.
- 완료 기준: 520px 이하에서 계산된 크기가 모바일 선언과 일치해야 합니다. 실제 넘침·줄바꿈은 렌더링 검증이 필요합니다.

## 최신 코드에서 확인한 개선점

- 조합 결과/오류 도착 시 자동 스크롤과 포커스 이동이 추가됐습니다. 이전 보고서의 결과 진입성 제안은 일부 반영된 것으로 정리합니다. 선택 경기별 요약/개별 제거 기능과는 별개입니다.
- 모바일 메뉴 스타일을 `.site-header nav`로 제한해 기간·지역 필터까지 같이 영향을 받는 범위를 줄였습니다.
- 리그별 검증 상태와 컵 대회 예측 제한을 UI에 설명하고, 시장 확률만 있는 경기 카드도 표시합니다.
- 시뮬레이션은 초기/계산 중/오류 상태를 구분하고 기본 자동 재생에서 reduced-motion 설정을 고려합니다.
- 선수 명단·결장 정보의 수집 시각과 해당 정보가 분석 모델에 반영되지 않는다는 설명이 마련되어 있습니다.
