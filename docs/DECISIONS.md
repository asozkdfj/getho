# 의사결정 기록 (ADR-lite)

각 항목: 옵션 → 선택 → 이유. 바꾸고 싶으면 해당 ADR을 갱신하고 영향 범위를 확인합니다.

## ADR-001 Python 패키지 경계

- 옵션: (a) 단일 패키지 (b) uv workspace 3개 패키지 `edge_ml / edge_api / edge_ingestion` (c) 서비스별 repo
- **선택: (b)**. `ml`은 DB와 HTTP에 의존하지 않아 독립적으로 테스트할 수 있고, ingestion은 API의 ORM을
  재사용합니다. lockfile은 하나(`uv.lock`)이고 Docker 이미지도 하나입니다. 나중에 DB 레이어를
  `packages/db`로 빼면 ingestion을 별도 서비스로 분리할 수 있습니다.
- 편차: 기획서 트리의 `infra/migrations/` 대신 마이그레이션을 `apps/api/migrations/`에 둡니다. ORM
  모델과 같은 패키지에 있어야 autogenerate와 `alembic check`가 단순해지기 때문입니다.

## ADR-002 odds_snapshots 형태

- 옵션: (a) selection당 1행(`selection, odds`) (b) 한 북메이커의 1X2 세트를 1행으로 (c) 헤더 + 가격 child 테이블
- **선택: (b)**. de-vig는 세트 단위로 해야 하고, `market_odds_snapshot_id` 하나로 예측이 쓴 가격 세트를
  정확히 가리킬 수 있습니다. O/U 같은 다른 시장이 추가되면 (c)로 확장합니다(`market` 컬럼은 이미 있음).

## ADR-003 Mock 일정 앵커링

- 옵션: (a) 고정 날짜 seed (b) 실행일 기준 상대 날짜 (c) 고정 4일 그리드에 앵커링한 상대 날짜
- **선택: (c)**. 언제 실행해도 오늘과 이번 주에 경기가 있고, 같은 4일 창 안에서는 결과가 바이트 단위로
  동일해 seed가 idempotent합니다. 창이 바뀌면 mock이 시즌을 "재일정"합니다. fixtures는 upsert로
  갱신되고 새 배당 스냅샷이 추가되는데, 실제 provider의 일정 변경과 같은 경로입니다. 일정은 4일마다 한
  라운드, 하루 2~3경기로 실제 EPL 패턴과 다릅니다(데모 목적).

## ADR-004 prediction 멱등 키

- 옵션: (a) 같은 날 1회 (b) `(fixture, model_version)` 최신 1개 덮어쓰기 (c) `(fixture, model_version, odds_snapshot, input_data_as_of)` append
- **선택: (c)**. 덮어쓰기는 금지 조건(과거 값 보존)을 어깁니다. 입력 데이터 시각을 키로 쓰면 재실행은
  no-op이 되고 입력이 바뀌면 새 snapshot이 쌓입니다.

## ADR-005 Elo와 Poisson 결합

- 옵션: (a) Poisson만 (b) 확률 수준에서 가중 평균(Elo에는 무승부 모델이 별도로 필요) (c) 골 득실 우위(supremacy) 수준에서 결합
- **선택: (c)**. 결과가 여전히 하나의 score matrix에서 나오므로 1X2 합이 1이고, O/U 같은 시장으로도
  확장할 수 있습니다. 가중치 0.6과 280 Elo/골은 초기값이며, Phase 2 walk-forward 검증에서 튜닝합니다.

## ADR-006 Web → API 통신

- 옵션: (a) 브라우저가 API 직접 호출(CORS, public URL) (b) 서버 컴포넌트 + same-origin proxy route
- **선택: (b)**. API 호스트를 비공개로 둘 수 있고, 이미지 하나로 모든 환경에 배포할 수 있습니다
  (런타임 env). 확률이 stale하게 캐시되지 않도록 `cache: "no-store"`를 씁니다.

## ADR-007 Next.js 버전

## ADR-009 API-Football provider 구현 방식

- **HTTP 클라이언트:** (a) httpx/requests 의존성 추가 (b) stdlib urllib + 주입 가능한 transport → **(b)**.
  의존성을 늘리지 않고, 테스트는 녹화 형식 payload로 오프라인 실행합니다.
- **배당 `captured_at`:** (a) 수집 시각(벽시계) (b) 응답의 `update` 필드 → **(b)**. (a)는 같은 가격을
  받을 때마다 중복 스냅샷을 만들어 idempotency를 깨뜨립니다.
- **배당 조회 단위:** (a) 경기별 `/odds?fixture=` (b) 리그+시즌 페이지 조회 → **(b)**. 경기 20개 기준으로
  요청이 20회에서 2회로 줄어 Free 한도에서도 운영할 수 있습니다.
- **provider 간 데이터 격리:** 목록, 학습, 예측을 `fixtures.provider = DATA_PROVIDER`로 한정합니다. 합성
  데이터가 실데이터 모델을 오염시키지 않게 하기 위해서입니다.
- **몰수(AWD)·부전승(WO):** `cancelled`로 매핑하고 스코어를 버립니다. 행정 스코어는 팀 강도와 무관합니다.

## ADR-010 승격팀 prior (모델 v0.2.0)

- 문제: 실데이터에서 승격팀(Hull City, Ipswich)이 리그 평균(Elo 1500, 공격/수비 1.0)에서 출발해 크게
  과대평가됐습니다(예: Fulham–Hull 원정 승 모델 37% vs 시장 20%).
- 옵션: (a) 승격팀을 강등권 수준에서 출발 (b) Championship 데이터를 추가하고 리그 간 수준 차이로 환산
  (c) 경고 표시만 → **(a)**. 축구 모델에서 흔히 쓰는 방법이고 코드 변경이 작으며 근거를 설명하기 쉽습니다.
  (b)는 정확도를 더 높일 여지가 있어 Phase 2 후보로 남깁니다.
- 기준: 직전 시점 하위 3팀(강등 슬롯 수)의 평균. 시즌 정보가 없거나 한 시즌뿐이면 이전 동작(리그 평균)을
  유지합니다. 승격·강등이 없는 데이터에서는 v0.1.0과 결과가 같습니다(테스트로 보장).
- 출력이 바뀌므로 `MODEL_VERSION`을 0.2.0으로 올렸습니다. 기존 v0.1.0 예측은 보존되고 새 예측이 따로
  쌓입니다.

## ADR-011 평가 방법과 모델 교체 규칙

- 문제: 모델을 바꿀 근거가 필요하지만, mock 데이터는 정확도 근거가 될 수 없습니다.
- 데이터: openfootball/football.json(CC0, EPL 2018-19..2025-26, 3,040경기). 과거 배당은 없습니다.
- 방법: 주 단위 refit walk-forward(`as_of` 이전 경기만 학습, 코드에서 assert). warm-up < 2020-21,
  검증 2020-21..2022-23(튜닝), 시험 ≥ 2023-24(한 번만 채점).
- 지표: log loss(주), Brier, RPS, 최다 확률 적중, 보정(ECE, reliability bins). 기준선(기본 비율, Elo만,
  Poisson만)과 같은 표본에서 paired bootstrap.
- 교체 규칙(`edge_ml.promotion`): 시험 구간 ≥ 300경기, log loss가 0.002 이상 개선되거나 개선 CI 상한이
  0 미만, Brier가 나빠지지 않고 ECE 증가 ≤ 0.01. 결과: 튜닝 후보와 temperature 보정 모두 기준 미달이라
  v0.2.0을 유지했습니다.

## ADR-012 오늘의 픽

- 규칙: 하루(KST) 최대 1개, 데이터 점검을 통과한 오늘 경기 중 분석 확률이 가장 높은 결과. 동률은 확률 →
  이른 킥오프 → HOME > AWAY > DRAW. 백테스트와 서비스가 같은 함수(`edge_ml.picks.select_pick`)를 씁니다.
- 기준 확률: 옵션 (a) 70/80% 고정 (b) 백테스트에서 정한 설정값 → **(b)**. 기본 0.55는 "픽이 나온 날 ≥ 100
  이면서 적중률 95% 하한 ≥ 65%"를 만족하는 가장 낮은 기준입니다(시험 구간 234/396일, 71.4%
  [65.3–76.8]). 더 높이면 적중률은 오르지만 픽이 드물어집니다(0.70: 76일, 85.5%).
- 고정: 옵션 (a) 요청 때마다 계산 (b) 선정 시각에 한 번 저장 → **(b)**. 결과를 보고 바꿀 수 없어야 이력이
  정직합니다. 유니크 키 + `ON CONFLICT DO NOTHING`으로 동시성·재시작·재실행에서도 하나만 생깁니다.
- 선정 시각: 09:00 KST(`PICK_PUBLISH_HOUR`). EPL 경기는 대부분 KST 저녁~새벽이라 그 전에 배당과 예측이
  갱신됩니다. 선정 전 요청은 `scheduled`.
- 취소·연기: 옵션 (a) 무효로 남김 (b) 다음 후보로 교체 → 기본 **(a)**, 설정(`PICK_REPLACE_ON_VOID`)으로
  (b). 교체는 새 revision으로 추가되고 원래 픽도 남습니다.
- 설명: 저장된 특성(Elo, 공격/수비 강도, 홈 이점, 예상 골)만 인용하는 템플릿. LLM은 쓰지 않으며, 쓰더라도
  확률을 만들지 않습니다.

## ADR-013 여러 리그로 확장

- **수집 단위:** (a) 리그별로 일정·배당 조회 (b) 날짜별로 모든 리그를 한 번에 → **(b)**. 리그가 수백 개라도
  일정은 하루 1요청이고, 배당은 경기 수에 비례합니다. 리그를 몇 개만 고른 경우(`API_FOOTBALL_LEAGUES`에 5개
  이하)는 리그별 조회가 더 싸서 그쪽을 씁니다.
- **과거 결과:** 리그마다 현재+직전 시즌을 한 번만 받고(backfill), 이후에는 매 실행의 3일 창으로 이어 붙입니다.
  처음 연결할 때 요청이 몰리지 않도록 실행당 리그 수 상한과 남은 일일 요청 하한을 둡니다.
- **모델:** (a) 모든 리그를 한 번에 학습(리그 간 수준 차이를 따로 추정해야 함) (b) 리그별로 같은 모델을 따로
  학습 → **(b)**. 사용자가 요청한 "동일한 예측 모델"을 그대로 쓰고, 리그 간 비교가 필요 없습니다.
- **컵 대회:** 예측하지 않습니다. 서로 다른 리그 팀이 섞여 있어 리그 하나의 전력표로 설명할 수 없습니다.
  리그 간 수준을 잇는 전역 레이팅(TODO)이 생기면 다시 검토합니다. 경기와 시장 배당은 보여 줍니다.
- **검증 표시:** 실제 경기로 백테스트한 리그만 "정확도 검증됨"입니다(시험 경기 300개 이상, 기본 비율 대비
  log loss 개선의 95% CI가 0보다 큼). 나머지는 같은 방식으로 분석하되 "검증 전"으로 표시하고 주의 문구를
  붙입니다. mock(합성) 리그는 절대 검증됨이 되지 않습니다.
- **오늘의 픽 후보:** 기본은 검증된 리그만(`PICK_LEAGUES=verified`). 검증하지 않은 리그의 확률로 "오늘 가장
  확실한 결과"를 고르면 근거 없는 정확도를 내세우는 셈이기 때문입니다. 기준 확률 0.55는 유지했고 근거는
  MODEL_EVALUATION에 있습니다.
- **분류:** 지역(국제·유럽·아시아·남미·북중미·아프리카·오세아니아) → 나라 → 리그. 나라→지역 대응표와 한국어
  나라 이름, 주요 리그 순서는 `edge_api/catalog.py`에 있습니다. 표에 없는 나라는 "기타"로 갑니다.

## ADR-014 선발 명단 정보

- **1단계(수집·표시):** 결장 정보(경기 2일 전부터)와 공식 선발 명단(킥오프 약 1시간 전), 끝난 경기의 선수별
  출전 시간을 append-only로 저장합니다. 명단 스냅샷은 내용 해시를 키로 써서 10분마다 확인해도 중복이 생기지
  않습니다. 화면에는 "평소 주전 중 몇 명이 빠졌는지"를 보여 주고, 모델은 쓰지 않는다고 명시합니다.
- **변수 설계:** (a) 선수 22명 조합을 직접 학습(경기 수가 턱없이 부족) (b) 선수 능력 평점(데이터·라이선스
  부담) (c) 감독의 선택이 드러나는 출전 시간 비중으로 선발 11명의 "평소 대비 강도" 한 숫자 → **(c)**. 설명하기
  쉽고 provider 무관하게 계산됩니다.
- **모델 결합:** 기대 득점에 log-선형 보정 두 계수(β 자기 팀, γ 상대)만 추가합니다. 기존 모델 구조와 1X2 합 = 1이
  그대로 유지됩니다.
- **판단 기준:** 기존 교체 규칙(ADR-011)을 쓰되, 분할 위치 하나에 결과가 좌우되지 않도록 세 분할(검증 끝 55·60·65%)
  모두 통과해야 "채택 가능"으로 봅니다(실행 전에 정함).
- **결과(2단계):** StatsBomb 2015/16 4개 리그 기준 채택 가능 조건은 만족했지만 효과가 작고 CI가 0을 포함합니다.
  서비스 반영(3단계)은 사용자 결정 사항이며, 더 큰 실데이터 표본으로 다시 재는 것을 권합니다.
- **오늘의 픽과의 관계:** 픽은 09:00 KST에 고정되고 그때는 명단이 없으므로, 명단 정보는 픽에 영향을 주지 않습니다.

## ADR-015 픽 과거 기록은 서비스 시점으로, 피로 변수는 미채택

- **상황**: QA(`codex/qa-latest-ui-review`)가 오늘의 픽 과거 기록이 "하루 전체 후보" 계산이라 실제 서비스(오전
  9시 선정, 이후 경기만)와 다르다고 지적했습니다. 또 정확도 개선의 첫 변수군으로 피로·휴식을 요청했습니다.
- **결정**:
  1. 백테스트에 결과 반영 지연(`result_delay`), 학습 시각(`fitted_at`), 선정 시각 재현(`decision_hour`)을 추가하고,
     화면·API의 과거 기록은 시점 재현 표(`daily_pick_timing_proxy`)를 우선 사용합니다. 하루 전체 계산은 참고로만
     남깁니다. 서비스 날짜 규칙(9시~24시)은 바꾸지 않았습니다.
  2. 새 변수군은 결과를 보기 전에 프로토콜·채택 조건을 커밋하고, 같은 표본·시간순 선택→후속 평가로만 판단합니다.
  3. 팀 일정 기반 피로·휴식 변수는 조건을 하나도 통과하지 못해 채택하지 않습니다.
- **결과**: 0.55 기준 과거 기록이 550/654일·75.3%에서 236/654일·72.9%로 바뀌어 보입니다. 운영 모델은 v0.2.0 그대로입니다.

## ADR-016 오늘의 픽 시간대: 오전 9시 → 다음 날 오전 9시

- **상황**: 오전 9시~당일 자정 규칙에서는 유럽 저녁 경기(한국 새벽)가 어느 날의 후보도 되지 못해, 서비스 시점
  재현 기준 픽이 나오는 날이 36%에 그쳤습니다.
- **결정(사용자, 2026-10-16)**: 픽 하루를 선정 시각(`PICK_PUBLISH_HOUR`, 기본 09:00 KST)부터 다음 날 같은 시각까지로
  바꿉니다. 자정~선정 시각 사이에는 전날 고른 픽이 현재 픽입니다. 새 픽의 `policy.window`에
  `publish_hour_to_next_day_publish_hour`를 기록해 이전 규칙의 픽과 구분합니다(이전 픽은 그대로 보존).
- **근거(연구 수치, 10개 리그 합산, 기준 0.55)**: 픽이 나온 날 236/654일(36%) → 503/647일(78%), 적중률 72.9% →
  74.6%(CI 겹침). 품질 검사는 재현하지 않은 시점 조건만의 재현입니다.
- **영향**: API `/picks/today`에 `window_start`, `window_end` 추가. 경기 목록의 "오늘" 탭(달력 하루)은 그대로입니다.

## ADR-017 시장 비교 결과를 그대로 알린다

- **상황**: 과거 배당(football-data.co.uk, GitHub MIT 사본)으로 처음 시장과 비교했습니다. 시장이 분석보다 정확했고
  (후속 log loss 0.9769 vs 0.9976), '차이 큼' 표시 결과의 평균 수익률은 −17%였습니다.
- **결정**: 측정 결과를 성과 페이지(`#market`)에 표로 보여 주고, 차이·기대값이 보이는 곳(경기 상세, 주목할 경기,
  가이드)에 "과거에는 시장이 더 정확했고 '차이 큼' 결과는 손해였다"는 문구를 넣습니다. 시장 결합(0.25 분석 + 0.75 시장)은
  기준을 통과했지만 시장 단독보다 나빠 채택하지 않습니다.
- **남은 결정(사용자)**: '차이 큼' 배지·기대값·주목할 경기를 유지할지, 바꿀지(예: "시장과 다른 경기"로 중립 표시),
  없앨지.

## ADR-018 오늘의 픽: 결정 시각 기준 입력, 정책 버전, 실제 성과의 조건

- **상황**: 픽 결정이 "가장 최근 예측"을 그대로 써서, 고정 시계(`edge pipeline --now <과거>`)나 수동 재실행으로
  결정하면 그 시각 이후 데이터로 만든 예측이 들어갈 수 있었습니다. 경기 시작 후에 기록된 픽도 실제 성과에
  섞일 수 있었고, 정책 버전은 `window` 키로만 암묵적으로 구분됐습니다.
- **결정**: (1) 후보 예측은 입력이 모두 결정 시각 이전인 것(`input_data_as_of <= now`)만 씁니다. 같은 입력이면
  같은 예측이 나오므로(멱등 키) 결정 시각에 있었을 예측과 같습니다. (2) 픽마다 `policy.version`(2 = ADR-016
  시간대 + 결정 시각 입력), `evidence.decided_at`, `evidence.last_collection_at`을 기록합니다. 버전이 없는 이전
  픽은 1로 봅니다. (3) 지난 픽 성과는 **경기 시작 전에 기록된 픽**(DB 시각 `published_at` < 킥오프)만 셉니다.
  나머지는 목록에 남기되 `recorded_before_kickoff=false`로 표시하고 `late_recorded`로 따로 셉니다. 데모(mock)는
  고정 시계로 도는 합성 데이터라 이 조건을 적용하지 않습니다(성과 근거가 아님).
- **하지 않은 것**: 수집 기록(`ingestion_runs`)은 결정 시각으로 거르지 않습니다. 실행이 끝난 시각을 실제 시계로
  남기므로, 방금 데이터를 모은 실행이 결정 시각 직후로 기록됩니다. 거르면 정상 운영에서 픽이 막힐 수 있습니다.
  → ADR-022에서 바꿨습니다(파이프라인이 자기 기록 뒤의 시각으로 결정하고, 수집 기록도 결정 시각으로 거름).
- **영향**: 모델·확률·선정 규칙(가장 높은 확률, 기준 미달이면 픽 없음)은 그대로입니다. API에 필드 2개가
  추가됐습니다(하위 호환).

## ADR-019 일정이 바뀐 경기와 부가 수집 실패

- **상황**: 날짜 단위 수집은 다른 날로 옮겨진 경기를 원래 날짜에서 더 이상 돌려주지 않아, 경기가 예전 킥오프
  시각의 "예정" 상태로 남고 그 경기에 걸린 오늘의 픽이 영원히 정산되지 않을 수 있었습니다. 또 팀 뉴스 수집의
  provider 오류 하나가 실행 전체(경기·배당·예측·픽)를 되돌렸습니다.
- **결정**: (1) 킥오프 4시간이 지났는데 예정/진행 중이고 이번 조회에 나오지 않은 최근 30일 경기는 id로 다시
  받아 갱신합니다(실행당 최대 100경기, 요청 한도가 낮으면 다음 실행으로 미룸). 돌려주지 않는 경기는 추측하지
  않고 개수만 기록합니다. (2) 픽의 경기가 픽 시간대(`evidence.window_utc`) 밖으로 옮겨지면 "fixture
  rescheduled"로 무효 이벤트를 추가합니다. 원래 픽 행은 바꾸지 않습니다(append-only). (3) 팀 뉴스는 savepoint
  안에서 수집하고, provider 오류면 팀 뉴스만 되돌린 뒤 오류를 실행 기록에 남깁니다. 핵심 수집 오류는 지금처럼
  전체를 되돌리고 실패로 기록합니다.
- **영향**: 모델·예측 확률에는 변화가 없습니다. 실제 API로는 아직 확인하지 않았습니다(TODO #33).

## ADR-020 언더/오버·핸디캡 확률은 표시하지 않는다

- **상황**: 국내 서비스처럼 언더/오버와 핸디캡 옵션도 보여 줄 수 있는지 사용자가 물었습니다. 운영 모델의 예상 골에서
  두 시장의 확률을 바로 계산할 수 있습니다.
- **결정**: 표시하지 않습니다. 사전 등록 실험(`981ccf3`, 9개 리그, 후속 2023-26)에서 언더/오버는 리그 평균보다
  확실히 낫지 않았고(CI 0 포함) 확률도 기준보다 어긋났습니다(ECE 0.036). 핸디캡은 북메이커 기준선에서 동전
  던지기보다 나빴습니다. 근거 없는 숫자를 "분석"으로 보여 주지 않는다는 원칙(ADR-011)에 따릅니다.
- **영향**: 서비스 변화 없음. 핸디캡·언더/오버 배당도 수집하지 않습니다(요청량·약관 부담만 늘어남).
- **다시 볼 조건**: 점수 분포 모델을 바꾸거나(이변량·음이항 등) 1X2에서 시장과의 격차가 줄면 같은 프로토콜로 재측정.

## ADR-021 확률 구간 표시와 자동 조합

- **결정(사용자, 2026-10-16)**: 가장 높은 결과의 분석 확률로 경기를 두 단계(65%+, 55~65%)로 은은하게 구분하고,
  조합 화면에 "경기 수 → 모두 맞을 확률이 가장 높은 조합"을 추가합니다. 배당 조건이 붙은 추천(예: 5배 이상)은
  보완 장치(시장 확률·과거 실적 표시) 없이 넣지 않습니다.
- **근거**: 과거 3시즌 시뮬레이션에서 구간 확률이 실제 적중과 맞았고(65%+ 구간 72% → 77%), 조건 없는 3경기 조합도
  실제 적중(33%)이 분석 확률(27%)보다 높았습니다. 배당 조건을 붙이면 분석 19% vs 실제 15%로 부풀려졌습니다
  ([QA 기록](qa/2026-10-16-confidence-and-auto-combo.md)).
- **범위**: 검증 리그만(데모 데이터는 전체 리그, 오늘의 픽과 같은 규칙). 파란색을 써서 초록(차이·주목할 경기)과 구분.

## ADR-022 결정 시각 이후 기록은 쓰지 않는다, 조합은 본 가격으로만 (Codex QA F1~F4)

- **상황**: Codex 독립 QA가 다음 네 가지를 재현했습니다.
  - F2: 결정 시각보다 늦게 만든 예측·배당·수집이 픽 품질 검사를 통과했습니다. 나이가 음수여도 "최대 나이 이하"로 통과했습니다.
  - F1: 조합 분석이 화면에서 고른 배당(2.06) 대신 그 뒤에 만든 예측의 배당(9.0)으로 조용히 계산됐습니다.
  - F3: 다른 날로 옮겨진 경기가 다음 수집에서 이미 진행 중·종료로 보이면 픽이 무효가 아니라 정산됐습니다.
  - F4: 응답하지 않는 최근 경기들이 재조회 한도를 계속 차지했습니다.
- **결정**:
  1. **품질 검사:** 예측 생성 시각과 입력 시각이 결정 시각 이하여야 합니다(`prediction_timely`). 배당과 수집은
     `0 ≤ 나이 ≤ 최대`여야 합니다. 시각이 없으면 실패로 봅니다. 수집 기록은 결정 시각까지 끝난 것만 씁니다.
  2. **파이프라인의 픽 결정 시각:** 파이프라인은 자기가 쓴 기록 뒤의 시각(`max(now, 실제 시계)`)으로 결정합니다.
     `--now`로 시각을 고정한 실행은 그 시각으로 결정하므로, 그 뒤에 기록된 입력으로는 픽을 낼 수 없습니다(재실행으로
     과거 픽을 만들지 않음). `created_at`은 계속 DB 시계로 남습니다.
  3. **조합:** 요청의 각 선택에 사용자가 본 `prediction_id`가 필수입니다. 최신 예측이 바뀌었으면 409로 거절하고,
     화면은 새로고침 버튼과 함께 안내합니다.
  4. **일정 변경 무효:** 픽 시간대 밖으로 옮겨진 경기는 상태(예정·진행 중·종료)와 관계없이 정산보다 먼저 무효 처리합니다.
  5. **재조회 순환:** 경기마다 마지막 재조회 시각(`fixtures.reconcile_checked_at`, 마이그레이션 0005)을 남기고,
     한 번도 묻지 않은 경기, 그다음 가장 오래전에 물은 경기 순으로 묻습니다.
- **테스트 시계**: 테스트는 고정 시각(`NOW`)으로 돌지만 DB 기본값은 실제 시각을 찍어서, 모든 입력이 "결정 뒤"로
  보였습니다. 테스트에서만 DB의 `now()` 기본값과 파이프라인 시계를 `NOW`로 맞춥니다(`conftest.py`). 운영 코드는
  DB 시각을 그대로 씁니다.
- **영향**: 모델·확률·선정 규칙은 그대로입니다. API 변경은 두 가지입니다.
  - `SelectionIn.prediction_id` 필수: 하위 호환이 깨지지만 웹이 유일한 클라이언트이고 같이 바꿨습니다.
  - 조합 409 응답 추가.
- **남은 위험**: DB 서버 시계가 앱 시계보다 파이프라인 실행 시간 이상 빠르면, 운영 파이프라인의 픽이 `prediction_timely`에
  걸릴 수 있습니다. 그때는 아무것도 몰래 쓰지 않고 "픽 없음"과 실패한 검사 이름이 기록됩니다.

## ADR-023 예측·픽을 만든 코드와 결정 기록 (Codex 준비도 감사 1·2)

- **상황**: Codex가 실제 저장 DB를 감사해 보니 `model_versions.git_sha`가 `local`이었습니다. 그래서 운영 예측이 어느
  소스에서 나왔는지 DB만으로 알 수 없었습니다. 원인은 두 가지입니다.
  - `docker compose up --build`를 직접 실행하면 빌드 인자가 비어 기본값 `local`이 됩니다(`make up`만 커밋을 넘김).
  - 같은 `local`인 채로 코드가 바뀌어도 같은 모델 버전 행이 재사용됐습니다.

  또 오늘의 픽 기록에는 후보별로 어떤 예측·배당 행을 언제 관측·저장했는지, 어떤 설정과 빌드로 결정했는지가
  모두 남지는 않았습니다.
- **결정**:
  1. **코드 지문:** 예측과 픽을 만드는 세 패키지(`edge_ml`, `edge_api`, `edge_ingestion`)의 `.py` 파일
     (경로 + 내용)로 SHA-256을 계산합니다(`edge_api.versioning.code_fingerprint`). git 없이도 정확한 코드를 가리키고,
     `edge code-fingerprint`로 아무 체크아웃에서나 같은 값을 계산해 커밋과 맞출 수 있습니다.
  2. **모델 버전 식별:** 모델 버전 식별 키에 지문을 넣었습니다(마이그레이션 0006). 코드가 바뀌면 새 행이 생깁니다.
     예전 행은 지문이 NULL입니다(당시 코드를 모름).
  3. **커밋 기록:** `local`·`unknown`·빈 값은 커밋으로 기록하지 않습니다. 로컬 git 체크아웃이 있으면 그 커밋을
     쓰고(수정 중이면 `-dirty`), 없으면 `unknown`과 경고 로그를 남깁니다. compose 기본값도 `unknown`입니다.
  4. **픽 manifest:** 픽 evidence에 `manifest`(버전 1)를 남깁니다.
     - 빌드(커밋, 지문), 모델 버전, 픽 설정과 그 해시, 의존한 수집 실행(id, 끝난 시각)
     - 범위 밖 경기 id, 후보 목록의 해시
     - 후보마다 예측 id, 모델 버전 id, 예측 생성 시각, 입력 시각, 배당 행 id·북메이커, 관측 시각(`captured_at`),
       저장 시각(`created_at`), 품질 검사 전체(통과 여부와 상세)

     픽이 없는 날도 같습니다. 픽 표는 append-only라 결정 당시 그대로 남습니다.
- **하지 않은 것**: 예측 행마다 지문을 따로 두지 않았습니다(모델 버전을 거쳐 연결됨). 학습 데이터 해시와
  결과 첫 관측 시각 이력은 아직 없습니다(Codex 권장 2번의 나머지, 수집 단계 변경이 필요).
- **영향**: 모델·확률·선정 규칙은 그대로입니다. API는 하위 호환 범위에서 바뀝니다.
  - `/health`에 `code_fingerprint` 필드 추가.
  - 모델 버전 응답에 `code_fingerprint`(nullable) 추가.
  - 배포 후 첫 예측 실행에서 새 모델 버전 행이 하나 생깁니다(식별 키가 바뀜).

## ADR-024 같은 시각 병행 기록 (shadow-v1, Codex 준비도 감사 3)

- **상황**: 시장이 분석보다 정확하다는 근거는 수집 시각이 불명확한 과거 배당과, 이미 본 이틀치 실데이터뿐이었습니다.
  오전 9시에 실제로 볼 수 있었던 입력만으로, 아직 오지 않은 기간에 비교해야 판단할 수 있습니다.
- **결정**: 오늘의 픽을 결정하는 순간, 같은 입력으로 다음 후보를 모든 창 경기에 대해 append-only 표
  `shadow_forecasts`(마이그레이션 0007)에 기록합니다.
  - 운영 예측
  - 같은 북메이커의 결정 시각 배당(관측·저장 모두 결정 이전)
  - 고정 결합(0.25 운영 + 0.75 시장)
  - 참고용 고정 보정
  - 비교할 수 없는 경기는 제외 사유와 함께 남김

  평가 기간·최소 표본·판단 기준은 기록 시작 전에 [사전 등록](experiments/shadow-forecasts-2026.md)했고,
  `edge shadow-report`는 그 기간이 끝나기 전에는 `provisional`로만 표시합니다.
- **하지 않은 것**:
  - 화면 표시, 픽 변경, 운영 모델 교체.
  - 후보는 미리 고정한 것만 씁니다. 10/17·18 결과를 보고 가중치를 조정하지 않았습니다.
- **영향**: 하루 한 번(픽 결정 시) 창 경기 수만큼 행이 늘어납니다. 기록이 실패해도 픽은 그대로 나오고, 실패는
  evidence `shadow`에 남습니다. API 계약은 바뀌지 않습니다.

## ADR-025 결과를 처음 안 시각과 정정 이력 (Codex 준비도 감사 2의 나머지)

- **상황**: `fixtures`에는 최신 상태만 남았습니다. 그래서 결과를 언제 처음 알았는지, 나중에 스코어나 일정이 바뀌었는지
  알 수 없었습니다. 예측의 `input_data_as_of`는 학습 결과의 마지막 **킥오프** 시각이라, 결과를 실제로 알게 된 시각의
  대리값일 뿐이었습니다.
- **결정**:
  1. **관측 이력 표:** 수집이 경기의 상태·킥오프·스코어 변화를 저장할 때마다 append-only 표
     `fixture_observations`(마이그레이션 0008)에 한 줄을 남깁니다. 마지막 관측과 같으면 남기지 않고, 라운드·시즌만
     바뀐 경우도 남기지 않습니다. 저장 시각(`created_at`, DB 시계)이 그 상태를 쓸 수 있었던 가장 이른 때입니다.
  2. **기존 경기:** 마이그레이션에서 현재 상태를 `updated_at` 시각으로 한 줄씩 채웁니다(`source="backfill"`).
     실제 첫 관측보다 늦거나 같은 상한이라, 결과를 실제보다 일찍 안 것처럼 보이게 하지는 않습니다.
  3. **조회:** `queries.result_first_observed`(결과를 처음 저장한 시각)와 `queries.result_history`(상태 이력,
     정정 여부)를 추가했습니다.
  4. **예측의 출처 정보:** 예측 `features`에 학습 결과 수, 마지막 킥오프, 결과를 처음 저장한 시각의 최댓값, 관측 기록이
     없는 결과 수를 남깁니다.
- **하지 않은 것**:
  - 학습 데이터를 고르는 규칙과 `input_data_as_of`(멱등 키의 일부)는 바꾸지 않았습니다. 바꾸면 운영 예측이 모두
    새로 만들어지고 학습 결과도 달라지는 모델 동작 변경이기 때문입니다.
  - 운영에서는 `prediction_timely`(생성 시각 ≤ 결정 시각)가 이미 학습 결과도 그 전에 저장됐음을 보장합니다.
  - 정산 뒤 결과가 정정된 경우의 처리는 TODO #41로 남겼습니다.
- **영향**: 모델·확률·픽은 그대로이고, API 계약도 바뀌지 않습니다. 수집할 때 바뀐 경기 수만큼 관측 행이 늘어납니다.

## ADR-026 선수 정보: 결장 없음과 모름을 나누고, 결정 시점에 알던 것만 쓴다 (Codex 준비도 감사 4)

- **상황**: 결장 정보는 결장자가 있는 팀만 기록했습니다. 그래서 "확인했는데 결장 없음"과 "확인 안 함"이 같아 보였고,
  화면도 둘 다 "아직 알려진 결장 선수가 없어요"였습니다. 또 같은 내용의 보고는 다시 저장하지 않아(내용 해시 중복 제거),
  결장 → 회복 → 결장처럼 이전 상태로 돌아가면 최신 상태가 틀리게 남았습니다. 출전 기록은 경기 시각과 별개로 언제
  수집했는지(`created_at`)만 있고, "그 시점에 알던 기록"으로 읽는 길이 없었습니다.
- **결정**:
  1. **세 가지 상태:** 결장 정보는 팀마다 `reported`(결장자 있음), `none_reported`(확인했고 없음), `unknown`(확인 안 함)입니다.
     - 공급자가 실제로 확인한 경기(`AbsenceReport.covered`)이고 리그에 결장 정보 제공 범위가 있을 때(`leagues.has_injuries`,
       API-Football `coverage.injuries`)만 빈 기록을 남깁니다.
     - 요청 한도로 건너뛴 날, 결장 정보를 제공하지 않는 리그, 아직 공개 전인 경기는 기록이 없고 `unknown`입니다.
  2. **이전 상태로 돌아가기:** 팀의 최신 기록과 내용이 다를 때만 새 줄을 남깁니다. 같은 보고를 다시 받으면 쓰지 않습니다
     (마이그레이션 0009에서 내용 해시 유일 키 제거).
  3. **시점 지정 읽기(`as_of`):** 팀 뉴스는 그 시각까지 수집되고 저장된 기록만, 출전 기록은 그 시각까지 저장된 것만 셉니다
     (7월 경기를 10월에 수집했으면 8월 결정에는 없던 정보).
  4. **화면과 API:** API에 `absences_status`를 추가했습니다. 화면은 "확인했는데 결장 선수가 없어요"와
     "아직 받지 못했어요. 결장 선수가 없다는 뜻은 아니에요"를 구분합니다.
  5. **준비도 리포트:** `edge team-news-coverage --start --end`는 날마다 09:00 결정 시점 기준으로 다음을 셉니다.
     결장 정보 상태(세 가지), 선발 명단 도착, 주전 판단이 가능한 팀 수.
- **선발 명단은 아침 픽과 분리합니다**: 오늘의 픽은 append-only로 결정 시점에 고정되고, 선수 정보를 쓰지 않습니다.
  선발 발표 뒤 갱신하는 분석을 만든다면 별도 제품·별도 평가로 두고, 아침 픽이나 그 기록을 덮어쓰지 않습니다.
- **하지 않은 것**: 선수 정보를 모델 입력으로 쓰지 않았습니다. 관측 xG 수집도 하지 않았습니다(Codex 권장 5번).
- **영향**: 모델·확률·픽은 그대로입니다. API에 필드가 하나 추가됐고(기본값 `unknown`, 하위 호환), 확인된 경기마다
  결장 없는 팀의 빈 기록이 늘어납니다.

## ADR-027 Codex 아침 QA 반영 (MORN-1~3, 0006 다운그레이드)

- **MORN-1:** 주전 판단의 출전 시간 집계에도 행마다 `created_at ≤ as_of`를 적용합니다. 전에는 최근 경기 선택에만
  적용돼서, 일부만 먼저 수집된 경기의 나중 행이 섞였습니다.
- **MORN-2:** API-Football 결장 응답에서 한 행이라도 읽을 수 없는 경기는 "확인됨"으로 보지 않습니다. 그 경기의
  나머지 행도 버려서, 부분 목록이나 빈 목록이 마지막 정상 기록을 덮지 않게 합니다. 경기를 알 수 없는 행이 있으면
  그날 전체를 확인하지 않은 것으로 둡니다.
- **MORN-3:** 병행 기록이 쓰는 추가 예측 조회까지 savepoint 안에 넣었습니다. 조회든 저장이든 실패해도 픽은 그대로
  나오고, 실패는 evidence에 남습니다.
- **0006 다운그레이드:** 지문만 다른 모델 버전 행이 있으면 예전 유일 키에서 충돌했습니다. 이제 다운그레이드가 첫 행을
  제외한 나머지의 커밋 표시에 지문 앞부분을 붙입니다(`unknown+bbbbbbbbbbbb`). 행은 예측이 참조하므로 합칠 수 없습니다.
  0009 다운그레이드 제약(이전 보고로 돌아간 기록)은 append-only라 그대로 둡니다.
- **병행 기록 리포트 보강:** 결정 지연, 주 단위 CI, 날짜별 기록 상태를 추가했고, `decisions`는 `final`일 때만 채웁니다.
  첫 기록(10/20) 전에 [사전 등록 문서](experiments/shadow-forecasts-2026.md)에 추가 절로 적었고, 주 판단 기준은 그대로입니다.

## ADR-028 결과를 보지 않는 수집 품질 리포트 (Codex 착수 조건 검토 3)

- **상황**: 병행 기록(shadow-v1)과 이후 선수 정보 실험은 수집이 매일 제대로 돌았다는 전제가 있어야 의미가 있습니다.
  그런데 실행 누락, 실패, 결정 지연, 결정 시점의 입력 가용성을 결과와 섞지 않고 볼 수단이 없었습니다.
- **결정**: `edge collection-quality --start --end [--interval-minutes]`를 추가했습니다. 픽 날짜마다 다음을 냅니다.
  - **실행:** 성공·실패 수, 실패 메시지 앞부분, 성공 실행 사이 가장 긴 공백, 예정 실행 수(워커 일정 기준)
  - **결정:** 그날 결정이 있었는지, 상태, 09시 이후 몇 분 뒤였는지
  - **결정 시점의 입력:** 경기 수, 예측과 배당이 있는 경기, 배당 나이(중앙값·최대·최대 나이 초과), 리그별 표본
    (상위 10개), 양 팀 결장 정보 상태, 병행 기록 행 수와 오류

  요약에는 결정 없는 날, 실패가 있는 날, 공백이 예정 간격의 2배를 넘는 날, 병행 기록 오류가 있는 날을 모읍니다.
  **스코어·적중·log loss는 읽지 않습니다.** 그래서 평가 기간 중에도 매일 봐도 결과를 엿보는 것이 아닙니다.
- **하지 않은 것**: 알림(TODO #34)과 화면 표시는 하지 않았습니다. 무경기일과 수집 장애는 경기 수와 실행 기록을 함께
  보고 사람이 판단합니다.

## ADR-029 경기 후 팀 통계(슈팅·유효 슈팅·xG) 수집

- **상황**: 사용자 실행 결과 API-Football은 검증 리그 10개 모두 최근 경기의 xG를 줍니다(40/40). 이 xG는 끝난 경기의
  출전 기록을 받는 같은 상세 응답(`/fixtures?ids=`)에 들어 있습니다.
- **결정**:
  1. **저장 표:** append-only 표 `match_statistics`(마이그레이션 0010)에 팀별 슈팅, 유효 슈팅, xG, 출처를 남깁니다.
     저장 시각(`created_at`)이 그 통계를 쓸 수 있었던 가장 이른 때입니다.
  2. **수집 시점:** 출전 기록과 **같은 요청에서** 함께 저장합니다(`get_post_match`, 추가 요청 없음). 출전 기록이나
     통계가 하나라도 없는 끝난 경기를 대상으로 하므로, 이미 출전 기록이 있는 최근 120일 경기도 차례로 통계가 채워집니다.
  3. **정정:** 공급자가 수치를 바꾸면 새 줄로 남깁니다(마지막 기록과 같으면 쓰지 않음). `queries.latest_statistics(as_of=)`는
     그 시각까지 저장된 것만 읽습니다.
  4. **과거 시즌 백필:** `edge backfill-appearances`가 같은 응답의 통계를 `source="backfill"`로 함께 저장합니다.
     당시에 알던 정보가 아니라는 표시입니다.
  5. **데모 데이터:** mock은 예상 득점 주변의 합성 통계를 만듭니다. 성과 근거가 아닙니다.
- **하지 않은 것**: xG를 모델 입력이나 화면에 쓰지 않았습니다. 실험은 데이터가 쌓인 뒤 사전 등록을 하고 진행합니다.
  수집 범위는 출전 기록과 같은 `TEAM_NEWS_LEAGUES`(기본은 검증 리그)입니다.
- **영향**: 모델·확률·픽은 그대로이고, API 계약도 바뀌지 않습니다. 끝난 경기마다 2행씩 늘어납니다.

## ADR-030 CLV(종가 대비 가치) 측정

- **상황**: 시장은 운영 모델보다 정확하고(후속 log loss 0.0207 차이), 분석 25% + 시장 75% 결합도 시장 단독보다 나빴습니다.
  같은 정보를 다듬어서는 시장을 넘기 어렵다는 뜻입니다. 시장을 넘을 수 있는지 판단하려면 먼저 모델에 시장이 모르는 정보가
  조금이라도 있는지 알아야 합니다. log loss 차이로는 수천 경기가 필요하지만, 배당이 모델 쪽으로 움직이는지(CLV)는 같은 표본에서
  더 민감합니다.
- **결정**:
  1. **측정 방법:** `edge backtest-clv`가 저장된 운영 모델 예측(다시 학습하지 않음)과 football-data.co.uk의 이른 배당·종가를
     경기 날짜와 팀 이름으로 잇고, 사전 등록한 부분 기울기 b_model(리그 평균 비율 쪽 되돌림을 함께 넣어 뺀 모델의 몫)과
     해석 규칙으로 보고합니다. 단순 기울기만 쓰면 이른 배당의 잡음 때문에 정보 없는 예측도 양수가 나오므로, 실제 데이터로
     처음 실행하기 전에 주 지표를 부분 기울기로 바꿨습니다.
  2. **결정 없음:** 결과로 모델·픽·화면을 바꾸지 않습니다. 양수 결과는 2단계(시장 가격을 출발점으로 두고 조정하는 모델)를
     사전 등록할 근거로만 씁니다. 이미 미채택된 확률 결합을 다시 채택하는 것이 아닙니다.
  3. **실행 위치:** 이 개발 환경은 football-data.co.uk에 접속할 수 없으므로 사용자 환경(docker)에서 실행하고, 요약 JSON만
     공유합니다. 원천 파일마다 SHA-256을 남깁니다.
- **한계**: 파일의 이른 배당 수집 시각이 공개되어 있지 않아 서비스의 오전 9시 판단과 같은 시점이 아닙니다. 종가가 이른 배당보다
  정확한지(sanity check)를 함께 보고해 열 의미가 가정과 맞는지 확인합니다. 실시간 확인은 병행 기록(shadow-v1)과 앞으로의
  배당 스냅샷으로 따로 할 수 있습니다.
- **영향**: 모델·확률·픽·API 계약은 그대로입니다.

## ADR-031 항상 켜진 개인 서버 (Tailscale 전용 접속)

- **상황**: 맥북이 꺼지거나 잠들면 수집이 멈춥니다. 병행 기록(shadow-v1) 평가 기간(2026-10-20~12-14)과 매일 픽 기록은 빠짐없는
  수집이 필요합니다. 사용자는 혼자만 보고 공유하지 않습니다. 앱에는 로그인 기능이 없습니다.
- **결정**:
  1. **서버 구성:** 클라우드 서버 1대(Ubuntu, 4GB)에 기존 docker compose를 그대로 올립니다. 서버 전용 차이는
     `docker-compose.server.yml` 덮어쓰기 파일에만 둡니다.
  2. **공개 포트 없음:** Docker는 호스트 방화벽(ufw)을 우회해 포트를 엽니다. 그래서 DB와 Redis는 호스트 포트를 없애고,
     API와 화면은 `127.0.0.1`에만 묶습니다. 화면은 `tailscale serve`로 내 tailnet 기기에만 HTTPS로 전달합니다.
     `tailscale funnel`(공개)은 쓰지 않습니다. 서버 방화벽은 SSH만 허용합니다.
  3. **잘못된 설정 차단:** `infra/server/deploy.sh`는 `DATA_PROVIDER=api_football`, 키 존재, 24자 이상 영문·숫자 DB 비밀번호,
     Compose 2.24.4 이상(`!reset`/`!override`)을 확인하고, 아니면 시작하지 않습니다.
  4. **운영 기본값:** 컨테이너 자동 재시작, 로그 크기 제한(10MB×5), 매일 `pg_dump` 백업(14개 보관)을 둡니다.
  5. **전환:** `dump-local.sh`가 맥북 수집을 먼저 멈추고 덤프한 뒤 맥북 스택을 끕니다. `restore.sh`는 빈 DB에만 복원합니다.
     두 곳이 동시에 수집하지 않게 하기 위해서입니다.
- **하지 않은 것**: 로그인 기능, 공개 도메인, 관리형 DB는 넣지 않았습니다. 혼자 쓰는 동안은 Tailscale이 접근 제어입니다.
  공유하려면 로그인 기능(TODO #15)이 먼저 필요합니다.
- **영향**: 앱 코드, 모델, API 계약은 바뀌지 않습니다. 로컬 `docker-compose.yml`도 그대로입니다.

## ADR-032 실시간 CLV 기록 (오전 9시 판단 → 킥오프 직전 배당)

- **상황**: 과거 CLV 측정(`edge backtest-clv`)은 파일의 이른 배당이 언제 수집됐는지 모릅니다. 서비스에는 병행 기록(shadow-v1)이
  픽 결정 시각에 본 운영 확률과 배당 스냅샷을, `odds_snapshots`가 이후 배당을 시각과 함께 누적합니다.
- **결정**:
  1. **측정 방법:** `edge live-clv`(`services/live_clv.py`)가 병행 기록의 `recorded` 행마다 결정 시각 배당(같은 북메이커)과
     **킥오프 전 마지막 스냅샷**을 비교합니다. 킥오프 뒤 배당(인플레이)은 종가로 쓰지 않습니다. 결정 뒤 새 스냅샷이 없으면 빼고 셉니다.
  2. **지표:** 과거 CLV와 같은 부분 기울기 b_model(`edge_ml.clv`)입니다. 평균 기준선은 결정 전에 끝난(킥오프 + 3시간) 같은 리그
     경기의 홈/무/원정 비율이고, 클러스터는 결정일입니다(주 단위도 보고). 단순 기울기, 배당이 모델 쪽으로 움직인 비율,
     '차이 큼' 결과의 평균 CLV는 참고로 냅니다.
  3. **결과 미사용:** 평가 대상 경기의 결과는 읽지 않습니다. 그래서 병행 기록 평가 기간에 매일 봐도 결과를 엿보는 것이 아닙니다.
     테스트가 결과를 바꿔도 보고서가 같은지 확인합니다.
  4. **결정 없음:** 모니터링 전용입니다. 양수 신호는 2단계(시장 가격 조정 모델) 사전 등록의 근거 중 하나로만 씁니다.
- **영향**: DB 스키마, 모델, 픽, API 계약은 그대로입니다.

## ADR-033 연구 페이지 (`/research`)

- **상황**: 수집 품질, 병행 기록 진행, 실시간 CLV를 터미널 JSON으로만 볼 수 있었습니다. 서버로 옮기면 휴대폰으로 보는 경우가 많아집니다.
- **결정**:
  1. **API와 화면:** `GET /research`(최근 1~31일 수집 품질, shadow-v1 진행, 실시간 CLV 요약)와 화면 `/research`(메뉴 "연구")를 둡니다.
     화면에는 지금까지의 실험 기록표도 고정 문구로 둡니다.
  2. **병행 기록 성적 비공개:** 병행 기록은 **보고서가 `final`이 되기 전에는 성적을 응답에 넣지 않습니다.** 경기 수, 대기 수, 제외 사유,
     결정 지연만 보여 줍니다. 평가 기간 중에 매일 성적을 보면 규칙을 바꾸고 싶어질 수 있기 때문입니다(사전 등록 보호).
  3. **CLV:** 실시간 CLV는 배당만 쓰므로 그대로 보여 줍니다(ADR-032).
- **하지 않은 것**: 로그인은 없습니다. 접근 제어는 서버의 Tailscale 전용 접속입니다(ADR-031). 차트는 넣지 않았습니다.
- **영향**: 운영 모델과 픽은 그대로입니다. API 계약에 `ResearchOut`이 추가됐습니다.

## ADR-035 슈팅 기반 전력 후보의 미래 경기 확인 (shadow-v2)

- **상황**: 슈팅 기반 전력 변수는 과거 실험에서 표준 기준을 통과했습니다(ADR-034). 하지만 후속 구간은 이미 본 기간이고, 서비스 입력
  (API-Football)이 학습 데이터(football-data.co.uk)와 다릅니다.
- **결정**:
  1. **기록:** shadow-v1은 고정된 그대로 두고, 같은 결정 순간에 `shadow-v2`를 따로 기록합니다
     (후보: production, market, production_shots_v1, [사전 등록](experiments/shadow-v2-2026.md)).
  2. **입력 조건:** 슈팅 변수 입력은 결정 시각까지 저장된 통계만 씁니다. 또 킥오프 + 3시간이 결정 시각보다 이른 경기만 씁니다.
     실험과 같은 코드(`edge_ml.shots`)이고, 계수는 모든 시즌으로 한 번 맞춰 고정합니다.
  3. **평가와 판단:** 평가는 결정일 2026-11-02~2027-03-28, 최소 1,500경기입니다. 판단은 표준 기준(+0.002, 결정일 CI 상한 < 0, Brier)이고,
     기간이 끝난 뒤 한 번만 채점합니다.
  4. **기록 실패 처리:** 기록이 실패해도 픽은 그대로 나옵니다. 실패는 evidence의 `shadow_v2`에 남습니다.
- **영향**: 운영 모델과 픽은 그대로입니다. `shadow_forecasts`에 하루 한 번, 픽 시간대 경기마다 한 줄이 추가됩니다.

## ADR-036 Codex 밤사이 QA 반영 (SHOT-1, STAT-1, CQ-1)

- **SHOT-1 (P1):** shadow-v2의 슈팅 이력과 live CLV의 리그 기준 확률은 통계를 결정 시각 기준으로 읽었습니다. 하지만 경기 상태·스코어·킥오프는
  현재 `fixtures` 행에서 읽었습니다. 그래서 나중에 정정된 결과가 과거 시점 재계산에 섞였습니다.
  - 이제 둘 다 결정 시각까지 저장된 최신 `fixture_observations`(ADR-025)를 씁니다.
  - 그 시각에 관측이 없는 경기는 넣지 않습니다.
  - 결정 시점에 이미 계산해 저장한 shadow 기록은 바뀌지 않습니다. 이 수정은 재현과 재계산을 위한 것입니다.
- **STAT-1 (P1):** 끝난 경기 통계는 경기에 한 줄이라도 있으면 완료로 봤습니다. 이제 홈·원정 팀을 각각 확인해, 한 팀만 저장된 경기는 다시
  수집합니다.
  - 남은 위험: 공급자가 한 팀 통계를 영구히 주지 않는 경기는 수집 창(120일, 백필은 지정 일수) 안에서 계속 다시 조회됩니다.
    통계가 아예 없는 경기는 원래부터 그렇게 동작했습니다.
  - 최신 경기부터 실행당 상한까지만 조회하므로 새 경기 수집은 밀리지 않습니다.
- **CQ-1 (P2):** 수집 품질 리포트의 리그별 집계를 리그 이름 대신 리그 ID로 합니다.
  - `leagues`는 `league_id`, `provider_id`, `country`, `name`과 숫자를 담은 목록입니다.
  - 이름이 같은 다른 나라 리그가 합쳐지지 않습니다.
- **기타:**
  - 테스트의 파일 읽기에 `encoding="utf-8"`을 명시했습니다(Windows 기본 인코딩).
  - 슈팅 실험의 경기별 확률 파일을 추가했습니다(MODEL_EVALUATION.md).
- **영향:** 모델, 확률, 픽, API 응답 형식은 그대로입니다. CLI의 수집 품질 JSON에서 `leagues` 형식만 바뀝니다.

## ADR-037 베트맨 배당 가상 비교기 A단계: 입력, 경기 연결, 규칙 목록

- **상황:** Codex 개발 명세 v0.1(`docs/qa/2026-10-20-betman-profit-simulator-development-spec.md`)은 모델 예측을 베트맨에서 실제로 살 수 있는 배당과 연결해 가상으로 검증하자고 합니다. 첫 PR은 A단계(입력 schema, 수동·파일 입력, 경기 연결, 공식 규칙 목록)만입니다.
- **결정:**
  1. **연구 전용, 구매 없음:** 실제 구매, 로그인, 결제, 자동 구매는 만들지 않습니다. 이 표들은 오늘의 픽과 모델에 쓰이지 않습니다.
  2. **append-only 표 4개 (마이그레이션 0011):** `betman_imports`, `betman_odds_snapshots`, `betman_event_mappings`, `betman_aliases`.
     - 정정은 새 줄로 남깁니다.
     - 경기 연결은 가격과 따로 저장합니다. 나중에 사람이 연결을 고쳐도 가격 기록을 건드리지 않기 위해서입니다.
  3. **관측 증거:** 베트맨에서 본 시각(`source_observed_at`)이 있는 가격만 `observed`입니다.
     - 나머지는 `historical_proxy`이며, 구매 가능 가격과 미래 경기 성과에 쓰지 않습니다.
     - 관측 시각을 지어내지 않습니다(`--observed-now`는 지금 본 가격에만).
  4. **경기 연결:** 이름만으로는 연결하지 않습니다. 자동 연결 조건은 다음을 모두 만족하는 것입니다.
     - 사람이 확인한 리그 별칭과 그 리그 안의 팀 별칭
     - 홈·원정 일치
     - 시작 ±2시간
     - 후보가 딱 하나이고, 같은 회차 다른 번호에 이미 연결되지 않음
     - 홈·원정이 뒤집히면 `rejected`, 후보가 여럿이면 `ambiguous`입니다. 사람의 결정은 자동 실행이 덮어쓰지 않습니다.
  5. **구매 가능 검사:** 다음을 모두 만족해야 구매 가능입니다. 그 시각에 저장돼 있던 최신 가격만 봅니다.
     - 연결됨, 관측 증거 있음
     - 관측과 저장이 모두 판단 시각 이전
     - 발매 중, 마감 시각을 알고 그 전, 시작 전
  6. **규칙:** 확인된 규칙 2개(고정배당, 정규시간 1X2)를 빼면 모두 미확인입니다(`docs/betman/RULES.md`). 미확인 규칙은 추정값으로 채우지 않고 `rules_unverified`로 표시합니다.
  7. **입력 방법:** CLI입니다(`betman-import`, `betman-map`, `betman-status`, `betman-rules`). 서버에서는 표준 입력으로 파일을 넣습니다. 자동 수집은 이용 조건 검토 전에는 만들지 않습니다.
- **영향:** 모델, 확률, 픽, API 응답은 그대로입니다. DB에 표 4개가 추가됩니다.
